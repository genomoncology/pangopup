# The cache is discarded when the setup that filled it changes

The model result cache recorded nothing about the software or the assets that filled it, so a row written by one setup answered a request made under another. The row key carried nine identity components, one of them a CPU policy. Ticket 0040 measured that no thread or worker setting moves any published field, so the old key threw away paid-for rows on a thread change and still served a row across an upgrade. The two callers disagreed as well: the command-line tool keyed on `CpuPolicy::production_default()` and the service keyed on the effective policy, so one variant on one set of assets landed in two different rows.

`CacheIdentity` in `crates/pangopup-cache/src/lib.rs` now names the assets a run reaches and nothing else. `CacheKey` is the submitted variant alone. A new `setup` table records the running software version beside the model, reference, mask, semantics, masking-policy and window values, as the readable text a reader sees rather than a digest that reader cannot check. `open_inner` reads that text back and compares it with the running setup once, when the file opens. Any difference sends the whole file to `remove_database_family` and reopens a fresh one, so no earlier row stays readable and no migration is attempted. `USER_VERSION` moved to 2 and `EARLIER_USER_VERSIONS` names the layout it replaced, so a file an earlier release wrote is recognized from its stamp before a table is read and discarded the same way. A foreign, damaged, or later-layout database at an explicitly named path is still refused and never deleted.

Both callers now report the discard on standard error, naming the file, so an operator can tell a cold cache from a broken one. `complete_model_batch` in `crates/pangopup-cli/src/main.rs` builds the setup once from the admission it already holds. `serve` in `crates/pangopup-cli/src/service.rs` reports from its first cache open only. Every later worker open finds the setup that open left, so three workers produce one report, and a service that keeps its cache says nothing.

The boundary held. No score value, position, status, reason or provenance field moved on either route. `scoring_identity` and `data_set_version` keep their values and their places. The cache still lives at `$XDG_CACHE_HOME/pangopup/model-results.sqlite3`, is still on by default, still takes `--model-cache` and `--model-cache-max-entries`, and a default file it cannot read is still recreated rather than fatal. The precomputed lookup route opens no model cache and did not change. `pangopup lookup` prints the same bytes.

Verified against real processes on the repository's miniature runtime fixtures in a scratch data root, with `XDG_CACHE_HOME`, `HOME` and `TMPDIR` redirected away from the operator's own cache. Filling a default cache with two variants and then changing the recorded software version, the model bundle, the reference bundle, or the mask each discarded the whole file, named it on standard error, and recorded the running setup in the file it left behind. No earlier row survived any of the four. A run under the same setup kept both rows, wrote nothing, and said nothing. A real 134-row cache an earlier release wrote was discarded and reported at the default location, at an explicitly named path, and under `pangopup serve`; each run exited 0 and still returned its answer. A foreign database, a damaged file, and a file stamped with a later layout each failed with `MODEL_CACHE_INVALID`, printed nothing on standard output, and were left byte for byte as they were. A command-line fill was found by a service running four model threads, and a service fill was found by the command-line tool, with one answer and no new write sequence in either direction. A service started on a different mask against a filled cache printed exactly one discard line naming the file across three workers, and printed nothing on the restart that kept it. The one added test target, `crates/pangopup-cli/tests/model_cache_setup.rs`, runs eleven tests in 0.75 seconds, which bounds what the suite's execution time can have gained.

Four findings stay open as drafts. 0061 records that the ambient-cache rule reaches one test file. 0062 records that a second process can refill a cache a running service still reads. 0065 records that a default cache thrown away for being unreadable is still silent, so on that one older path an operator still cannot tell a cold cache from a broken one. 0066 records that nothing forces the next replaced layout onto the earlier-layout list. Drafts 0060, 0063 and 0064 closed inside this ticket.
