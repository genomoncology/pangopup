# The cache reports every file it destroys, and its layout list cannot rot

Ticket 0058 made a default cache discarded for a setup change say so. A default cache destroyed because this build could not read it said nothing, and both destructions cost the same rows. `ModelResultCache::open_default` now records that second cause on the cache it hands back, `discarded_unreadable_file()` reads it, and both entry points print `discarded model cache <path>: this build could not read it` beside the setup-change sentence they already printed. The two causes are never reported as each other: an operator told that another setup filled a corrupt file goes looking for an upgrade nobody made.

Nothing else moved. A cold open and a matching open still say nothing. An explicitly named cache that cannot be read still refuses with `MODEL_CACHE_INVALID` and is never deleted. The whole file is still discarded, no earlier row is kept readable, and no migration was added.

The layout list has a gate behind it. `USER_VERSION` and `EARLIER_USER_VERSIONS` appeared nowhere else in the checkout, so a bump that dropped the layout it replaced passed every gate once already. `tests/model-cache-layout-history.sh`, in `make test`, reads every tag and every commit that touched `crates/pangopup-cache/src/lib.rs` for the layout it stamped and the on-disk shape it wrote, and refuses the tree when that pair disagrees with the running source. It exercises seven fixture refusals and four acceptances before it reads the real history, refuses a source whose constants cannot be read rather than passing on a scan of nothing, and refuses a shallow clone. It counts distinct layout states rather than commits, so the number cannot climb on a reflowed comment or hide a squashed history: `examined 3 distinct earlier layout state(s) against layout 2`. CI checks out full history for it. A unit test reads the list rather than spelling it, so a layout appended to it is proved when appended.

Exercised beyond the suite, on both entry points, under a private `HOME`, `XDG_CACHE_HOME` and `TMPDIR`. Six ways to reach a default cache this build cannot read — a truncated file, a flipped header magic, plain garbage, another application's stamp, a later layout, and an earlier layout — were driven through `pangopup lookup --model-only` and through a real `pangopup serve` started on its own default cache. Every unreadable form named the file and gave the unreadable reason; the earlier layout named the file and gave the setup-change reason; the answer was still returned and the file refilled with the row that run wrote. A zero-length file and a garbage write-ahead log stayed silent, which is the truth: neither destroyed a row. The same damage on an explicit `--model-cache` refused and left the file byte-for-byte, and a directory standing where the cache file belongs refused rather than being removed. A cache home whose path contains a space was reported verbatim.

Deleting the service's report branch leaves sixteen of the seventeen service fixture tests green. The code-review stage measured that the design's deferral to existing coverage was false — every other service fixture test passes `--model-cache`, which never sets the flag — and authored the one test that closes it. It stays.

One finding is filed rather than fixed. `sdlc/tickets/drafts/0074-a-cache-destroyed-mid-run-is-still-destroyed-in-silence.md`: `ModelResultCache::get` catches a SQLite failure on a disposable default cache and calls `recreate_default`, which removes the file and reopens it empty without setting either flag. Both call sites read the flags once, before any lookup runs, so reporting it needs a second report point that this ticket did not ask for.
