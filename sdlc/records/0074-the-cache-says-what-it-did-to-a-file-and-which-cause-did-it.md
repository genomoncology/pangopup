# The cache says what it did to a file, and which cause did it

Three cache events that cost an operator rows now name the file and the cause. A file discarded because this build reads its on-disk shape as an earlier layout gets its own flag, `discarded_earlier_layout()`, and its own sentence, `discarded model cache <path>: an earlier layout wrote it`. It is no longer reported as another setup, which sent the operator after an asset change nobody made and away from the release note that explains it. A disposable default cache that becomes unreadable after it was opened says `destroyed model cache <path>: it could not be read after it opened` at the moment `recreate_default` removes and reopens it, every time it happens, because every destruction costs its own rows. A process that stops using a file another setup replaced underneath it, or whose path no longer names a file it can open, says `stopped using model cache <path>: it no longer holds the file it opened, so restart to use what is there now` once for the process across the handler cache and every worker cache. Nothing is destroyed there, so the sentence names the restart rather than a discard.

The two sentences ticket 0067 settled are unchanged in wording and in cause, and the command line and the service print the same text for the same cause. A cold open, a matching open, a run that destroys nothing, and a process that takes up a replacement recording its own setup all stay silent.

Exercised beyond the suite under a private `HOME`, `XDG_CACHE_HOME` and `TMPDIR`, on both entry points. `pangopup lookup --model-only` was driven over a cold cache, a warm one, a file stamped `user_version=1`, a file another asset setup filled, and a file overwritten with random bytes: the first two said nothing, the last three printed the layout, setup and unreadable sentences respectively, and every run still answered and refilled the file. A real `pangopup serve` was started on each of the same five files and said the same five things. A running service whose default cache lost its row table in place, without the file being replaced, printed the destruction sentence and went on answering; damaging it a second time printed it a second time. A running service whose named cache file was replaced by a second process running other assets printed the retirement sentence once across four following requests, and once across twelve requests with four model workers. Deleting the cache file outright retired it on the same sentence. Replacing the default with a file recording the same setup was taken up in silence, as ticket 0068 settled.

`make lint`, `make test`, `make spec`, `scripts/run-service-fixture-tests.sh` and `sdlc/scripts/lint` all pass on this candidate. Nothing else moved: no answer, no score, position, status, reason or provenance, no row key, no recorded setup, no cache location, no default, no flag, and no change to when or what a run destroys. An explicitly named cache this build cannot open still refuses with `MODEL_CACHE_INVALID` rather than being recreated.
