# 054 — Prepare the v0.3.0 application release candidate

Status: ready

## Why

Current `main` contains the safe uninstall command and measured deployment
evidence, but published application version `0.2.0` cannot deliver those
changes. The README is accurate but still longer and more repetitive than the
ordinary install/use path needs to be. This ticket creates one coherent
`0.3.0` application candidate whose version surfaces, user guide, release
notes, tests, and maintainer state agree. It does not publish or tag anything.

## Scope

- Change the workspace application version from `0.2.0` to `0.3.0`, including
  workspace crate lock entries and every current application-facing assertion:
  `pangopup --version`, `pangopup -V`, `pangopup lookup --version`,
  `pangopup-build --version`, `/v1/status`, executable smoke tests, current
  container tags, and active workflow metadata.
- Preserve immutable historical records and tests whose subject is the
  already-published `v0.2.0` release or Ticket 050/051 evidence. A historical
  `0.2.0` string is not a version-bump target merely because it exists.
- Rewrite `README.md` as a first-use guide organized in this order:
  1. what PangoPup does and lookup-first/model-fallback behavior;
  2. exact download, installed-disk, and measured-memory requirements;
  3. direct Linux install and asset sync;
  4. CLI scoring and result provenance;
  5. foreground HTTP service with complete `curl` examples;
  6. Docker on AMD64 and Apple Silicon;
  7. update and safe uninstall;
  8. limitations, security, licenses, and maintainer links.
- Keep the README at no more than 350 lines and 2,200 words. Remove repeated
  engineering history while retaining all executable first-use contracts.
- State exact authenticated sizes from Ticket 053:
  - SNV download 1,931,694,270 bytes and installed member 15,033,158,255;
  - runtime download 691,874,664 bytes and installed members 812,662,222;
  - combined download 2,623,568,934 bytes and installed core members
    15,845,820,477.
- Explain mmap plainly: the installed fixed-width index is intentionally larger
  than its compressed download; mapping 15 GB reserves address space but Linux
  reads only touched pages, and mapped/file-backed bytes are not 15 GB of Rust
  heap or permanently resident RAM.
- Report Ticket 053 as one warm-cache Ryzen/Linux observation, not a universal
  guarantee: fresh SNV CLI median/maximum elapsed and peak RSS; ready service
  PSS/RSS/high-water RSS; 1/10/100 SNV HTTP latency; uncached model latency;
  and fresh-service SQLite-hit latency. Link the retained report and recommend
  operational headroom rather than turning the observed peak into a hard
  minimum.
- Create `planning/artifacts/054-release-notes.md` for v0.3.0. Name uninstall,
  read-only status/help/sync improvements since v0.2.0, measured resource
  guidance, unchanged biological/assets contract, supported delivery forms,
  and known Apple CPU warning.
- Reconcile current-state documentation:
  - `AGENTS.md` and `planning/faq.md` must no longer say GHCR is unpublished;
  - `architecture/service.md` and `architecture/delivery.md` must distinguish
    current public v0.2.0 history from the prepared v0.3.0 candidate;
  - close `planning/issues/2026-07-24-runtime-asset-trust-and-durability.md`
    with concise evidence for held descriptors, coherent profile activation,
    durable public compiled assets, and explicit non-syncing service startup;
  - update `planning/frontier.md` to make publication/qualification—not README
    or measurement—the next outcome.
- Update `spec/readme-first-use.md`, `spec/cli.md`, `spec/container-image.md`,
  current version-sensitive Rust/shell tests, and
  `.github/workflows/publish-container.yml` to enforce the candidate. Do not
  weaken current install, scoring, HTTP, Docker, security, attribution, update,
  or removal checks merely to shorten the README.
- Do not rebuild or republish biological assets, create a Git tag/release,
  upload a package/image, or move `latest` in this ticket.

## Decisions

1. **Use semantic version `0.3.0`.** `0.3` is not the repository's accepted
   release grammar. This is an application release; biological assets keep
   their immutable independent identities.
2. **One version across executable and container.** Publishing the two from
   different source commits created avoidable v0.2.0 provenance ambiguity.
   Ticket 055 will publish both from the exact candidate commit prepared here.
3. **Observed resource table, not requirements theater.** Ticket 053 gives a
   trustworthy single-host warm baseline. The README will state those numbers
   and sensible free-disk guidance without claiming every host needs exactly
   the observed RSS or has the same latency.
4. **Shorten by moving history, not by deleting operational answers.** The
   README remains the copy/paste user guide. Architecture, provenance, and old
   release narratives stay linked in tracked documents rather than repeated.
5. **Prepare but do not publish.** Version changes, docs, and release notes are
   reversible repository work. Tagging, GitHub release creation, and GHCR tag
   mutation remain Ticket 055's separately reviewed public effect.
